# Clean installation and container validation — 2026-10-08

## Scope

Reference: the existing Oracle Ubuntu 26.04 server, inspected read-only.
Native candidate: an isolated Ubuntu 24.04 VM with 2 vCPU, about 1 GiB RAM,
2 GiB swap and a 22 GiB root filesystem. No production accounts, private
configuration, certificates, mailbox or original ROMs were imported.
The repository baseline was `c605bb9` on `feature/full_server`; installation
changes in this report are the subsequent installation/SDK batch committed
with this report.

## Native installation

All six scripts completed. Re-running from the `/opt/reon` symlink also
completed after fixing physical path resolution. HTTP `/login.php` returned
200. nginx, PHP-FPM, MySQL, Postfix, Dovecot, mail effects, relay policy and
mobile-relay were active. Eleven REON timers were enabled, including patch
build and backups. Optional patch toolchains installed; original ROMs remain
an operator input, so no real patch artifact was validated.

Mail used `TLS_MODE=disabled` and `MAIL_MODE=internal` with synthetic accounts.
SMTP delivery, refusal of external recipients, POP3 APOP using a device key
and gID, retrieval and deletion passed before and after reconfiguration.
The banner follows the configured mail domain. No Internet email or TLS
certificate issuance was exercised.

All five fail2ban jails were loaded. The scanner filter matched `.env` and
`.git/config` fixtures, while an ordinary `/cgb/` 404 did not match. The jail
has a one-request threshold. Admin controls were exercised as the actual
PHP user, `reon`; the helper's journal action worked. A documentation-range
address was correctly refused by the manual ban helper. This is not evidence
of host ingress filtering or a live scanner ban.

Adapter settings initialize with the installation's IPv4 address and preserve
existing values on rerun. They no longer fall back to Oracle's public address
on a fresh installation.

Package versions differ intentionally by supported Ubuntu release. Dovecot
2.3 uses its own configuration syntax, with an authentication query derived
from the canonical 2.4 template. This does not claim binary/package identity.

All 510 Oracle column definitions (name, type and nullability, including
views) were present on the VM. The VM had 519: nine additional columns in the
retired `sys_inbox` table, retained by the historical migration for legacy
compatibility. No table was destructively dropped. This comparison does not
establish identical indexes, database data or every query plan.

The clean-install gaps discovered and brought into the normal workflow were:

- `sys_settings` existed only through a maintenance SQL file. A migration
  now creates it and retains existing operator preferences.
- Phinx's MySQL adapter created the Stadium payload as BLOB despite the
  requested varbinary limit. A guarded migration sets VARBINARY(4094),
  refusing oversized values rather than truncating them.
- Two Nodemailer lockfiles disagreed with their package manifests. The three
  mail apps now pin Oracle's Nodemailer 10.0.9; four workers pin Oracle's
  mysql2 3.24.2. Automatic audit rewriting is an explicit opt-in. Every declared direct Node
  dependency in the five applications matched the Oracle-installed version
  after the final VM rerun.
- .NET's channel selection picked a newer SDK. Its default is now pinned.
- Fresh config file groups blocked service reads; runtime config uses 0640
  and the `reon` group, while `.env` and backups remain private.
- A symlink invocation could link `/opt/reon` to itself.
- Admin user discovery did not follow symlinked nginx configuration.
- apt operations could fail while unattended updates held the package lock.
- Cached runtimes did not recreate command symlinks in a new container;
  Node/npm/npx and dotnet symlinks are now restored on the cached path.

567 selected tracked source files were hashed against Oracle; 565 existed
there. Differences in inspected PHP application/migration files were comments
and documentation, including SQL comments; their executable token comparison
passed. The seed helper has a help-text difference. Runtime rotation state,
lockfiles and the changed installer are not byte-identical. Two maintenance
files absent on Oracle are not missing application endpoints. This is scoped
source evidence, not an exhaustive game/hardware regression.

## Dummy SDK

The `dummy-server` target is Node only, with no npm dependencies or real
mail/database services. Its local smoke gate passed binary download byte
identity, POST fixture response, internal SMTP, external recipient refusal,
USER/PASS and APOP aliases, raw MIME/dot-stuffing, committed deletion and DNS A.
SMTP AUTH PLAIN was also exercised with the eight-character fixture password.
The final image was about 158 MB uncompressed and used about 9–10 MB RAM idle.
These are local measurements, not limits or cross-platform guarantees.
CI publishes this target after the same smoke gate. The workflow itself has
not yet run remotely at the time of this local validation.

## Production container

The production profile uses Ubuntu 24.04 and systemd with the actual native
scripts, real MySQL/Postfix/Dovecot, workers, relay and optional patch tools.
An isolated first boot completed, with web 200 and the same mail gate passing.
The image contains no runtime credentials: synthetic config was mounted at
boot. Host swap, SSH, firewall/fail2ban and monthly host reboot are outside
this container and must be managed by the operator/runtime.

The recreation test exposed why `/var/lib` must not be persisted wholesale:
the dpkg database would survive without package binaries. The profile now
persists individual application data directories. After the runtime symlink correction, replacement over the persisted data
completed: both fixture accounts, a custom adapter setting and mailbox content
survived; the mail gate passed again, and no failed systemd units remained.
A message deferred while Dovecot was stopped survived another replacement
in the persisted Postfix queue and was delivered after startup; the queue
then became empty. Test containers, their anonymous volumes and build images
were removed after validation, including all twelve test containers and
twenty-eight captured anonymous volumes. Existing unrelated images/containers
were retained. The SDK also stopped on SIGTERM with exit code 0. VM fixture accounts were erased through the
application account deletion routine.

## Remaining boundaries

No production deployment occurred. No original-ROM output, physical Game Boy,
public DNS/TLS, Internet mail deliverability, backup restore or host ingress
security was validated. A clean installation does not contain the live
server's users or published content; those are a separate authorized migration.
